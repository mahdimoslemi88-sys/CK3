# قوانین گردش‌کار وزیر (Vizier Workflow)

این قوانین برای سرعت‌بخشیدن به دیوان و حل مسائل ناشناخته وضع شده‌اند و رعایت آن‌ها الزامی است:

## ۱. استخراج سریع و بی‌درنگ سیو

هر زمان بازیکن درخواستی داشت، **اولین اقدام** اجرای ابزار پروژه است:
- **اقدام:** اجرای `python extract_save.py extract` (خودش جدیدترین سیو را انتخاب می‌کند؛
  `autosave_exit` به‌صورت پیش‌فرض نادیده گرفته می‌شود).
- خروجی این فرمان (نسخهٔ جدید، تک‌منبع):
  - `reports/state_report.txt` — گزارش فارسی کامل + بخش‌های ساختاریافتهٔ مرحله ۲ تا ۴
  - `reports/state_report.json` — **خروجی machine-readable اصلی برای همهٔ تحلیل‌ها** با ۱۳ بخش:
    `meta, player, domain, counties, holdings, characters, vassals, factions, succession, wars, military, court, quality`
  - `reports/history/snapshot_<game_date>.json` — اسنپ‌شات وضعیت؛ هر سیو تازه یک فایل جدید
    (re-extract همان سیو همان فایل را بازنویسی می‌کند) — خوراک `ck3-trend-analyst` و مقایسه‌های افت کیفیت `ck3-data-steward`.
- اگر خروجی از قبل موجود است و سؤال دربارهٔ «الان» است، اول `meta.game_date` و
  تاریخ فایل را با سیوی که بازیکن می‌گوید بسنج؛ اگر قدیمی بود، دوباره extract کن.

## ۲. قاعدهٔ حیاتی داده (برای همهٔ ساب‌ایجنت‌ها، بدون استثنا)

- **منبع تحلیل = `state_report.json`.** بخش متنی (`state_report.txt`) برای انسان است؛
  اعداد و ادعاها را از JSON بیاور تا دو منبع متناقض ساخته نشود.
- **گم‌شده ≠ صفر:** هر فیلد `null` یا غایب یعنی در سیو ذخیره نشده. قبل از قضاوت
  `quality.missing_fields` و `quality.warnings` را بخوان. مثال واقعی این ذخیره:
  `player.faith` ذخیره نمی‌شود؛ سطح ساختمان‌ها `unknown` است؛ نظر عددی رعایا موجود نیست.
- **هیچ عددی ساختگی نیست:** امتیاز جنگ فقط از `ticking_war_score` و `war_score_sum`
  (نبردهای ثبت‌شده)؛ وارث فقط از `succession.succession_line` ذخیره‌شدهٔ بازی؛
  خطرناکی فکشن فقط از `power_over_threshold` یا هشدارِ صریحِ نبودِ آستانه.
- `quality.sources` منبع هر بخش را می‌گوید؛ اگر سؤالی فراتر از آن منابع بود،
  صریح بگو «از این خروجی قابل استخراج نیست» و پیشنهاد جمع‌آوری دادهٔ تازه بده.

### هفت اصل مشترک همهٔ ایجنت‌ها (فعلی و آینده — الزامی)

1. **اول `quality`، بعد تحلیل** — هیچ ایجنتی قبل از خواندن `missing_fields`/`warnings`/`counts` نتیجه ندهد.
2. **هر عدد با مسیر JSON** — عددِ بی‌منبع ممنوع؛ شمارش دستی ممنوع، `quality.counts` مرجع رسمی است.
3. **برچسب منبع روی هر ادعا** — «سیو» / «ویکی» / «فرضیه — دانش بازی»؛ خلط این سه ممنوع.
4. **null ≠ صفر** — دادهٔ غایب یعنی «قابل ارزیابی نیست»، نه صفر و نه بد.
5. **قالب پاسخ واحد — «کارت فرمان»** — هشدارهای فوری ← تحلیل موضوعی ← حداکثر ۳ **کارت فرمان**.
   هر کارت فرمان ۷ فیلد الزامی دارد (فیلد ندارد = کارت نیست، تحلیل است):
   ```
   کارت ۱ — <فعل قابل اجرا در بازی>
   مسیر اجرا: <منو/سازوکار دقیق در بازی، مثلاً «دیوان ← منصب ↠ ...» یا «کلیک راست روی شهرستان ↠ ...»>
   هزینه: <مقدار + واحد از player.resources؛ اگر متغیر است، بازه و شرط آن — بدون عدد ساختگی>
   اثر: <چه چیزی در سیوی بعدی باید تغییر کند — فیلد JSON هدف>
   پیش‌نیاز: <شرط‌های عددی که همین حالا در JSON قابل چک است>
   ریسک: <پیامد منفی ممکن + مسیر JSON که آن را در سیو بعد می‌سنجیم>
   منبع: سیو / ویکی / فرضیه — دانش بازی (برچسب اجباری)
   ```
   و در پایان هر پاسخ، سطر «برای سیو بعدی چه عددی باید تغییر کند» الزامی است —
   این سطر حلقهٔ بازخورد بین سیوهاست و خوراک مستقیم `vizier_trends` می‌شود.
6. **فارسی یکدست** — واژگان از `ck3-persian-terminology`.
7. **جدول تصمیم‌گیری عددی در هر حوزه** — الگوی فصل ۸ راهنما: شرط عددی + مسیر JSON + اقدام پیشنهادی.

## ۳. ساب‌ایجنت‌های تخصصی و اسکیل‌های الزامی آن‌ها

دیوان دارای ۴ ساب‌ایجنت رسمی است که هر کدام موظف به مطالعه و رعایت اسکیل‌های حوزهٔ خود هستند.
همهٔ ساب‌ایجنت‌ها **اول** `ck3-alert-priorities` (نسخهٔ جدید، مبتنی بر quality) را اجرا می‌کنند،
سپس اسکیل تخصصی خود را فقط روی `state_report.json` اعمال می‌کنند:

| ساب‌ایجنت | نقش تخصصی | بخش‌های JSON | اسکیل‌های الزامی |
| :--- | :--- | :--- | :--- |
| **`vizier_economy`** | وزیر اقتصاد و عمران | `player, domain, counties, holdings` | `ck3-economy-strategy`<br>`ck3-development-holdings-terrain`<br>`ck3-clan-government`<br>`ck3-persian-terminology` |
| **`vizier_military`** | وزیر جنگ و فتوحات | `military, wars, court, player` | `ck3-warfare-combat-mechanics`<br>`ck3-military-strategy`<br>`ck3-persian-terminology` |
| **`vizier_diplomacy`** | وزیر دیپلماسی و جانشینی | `succession, relations, dynasty, opinions, characters, vassals, player` | `ck3-diplomacy-strategy`<br>`ck3-dynasty-renown-legacies`<br>`ck3-succession-realm`<br>`ck3-iranian-intermezzo`<br>`ck3-persian-terminology` |
| **`vizier_intrigue`** | وزیر اطلاعات و امنیت | `factions, schemes, secrets, artifacts, court, characters, player` | `ck3-factions-civil-wars`<br>`ck3-stress-mental-breaks`<br>`ck3-religion-faith-mechanics`<br>`ck3-alert-priorities`<br>`ck3-persian-terminology` |
| **`vizier_trends`** | تحلیل‌گر روند (جهت حرکت بازی بین دو سیو) | `reports/history/snapshot_*.json` (همهٔ بخش‌ها) | `ck3-trend-analyst`<br>`ck3-alert-priorities` |
| **`vizier_data`** | نگهبان داده (سلامت خروجی و قرارداد اسکیل↔JSON) | `quality, meta` + همهٔ بخش‌ها برای سازگاری شمارنده‌ها | `ck3-data-steward` |

**الزام عملیاتی برای همهٔ ساب‌ایجنت‌ها (بدون استثنا):**
1. هر اقدام پیشنهادی باید در قالب **کارت فرمان ۷ فیلدی** (اصل ۵) ارائه شود؛
   «توصیهٔ» بدون مسیر اجرا، هزینه و اثرِ قابل‌سنجش ممنوع است.
2. قبل از پیشنهاد هر اقدامِ پرداختی، **توان پرداخت** از `player.resources`
   چک شود (طلا/تقوا/شکوه — فیلدِ غایب یعنی قابل ارزیابی نیست، نه صفر).
3. هر کارت باید سطر **«برای سیو بعدی چه عددی باید تغییر کند»** داشته باشد؛
   این اعداد، خوراک مقایسهٔ `vizier_trends` در اسنپ‌شات بعدی هستند.

### تقسیم‌بندی داده (جلوگیری از تحلیل موازیِ متناقض)

- `vizier_military` تنها مرجع تفسیر `wars[]` و `military` است (جنگ‌های فعال فقط از
  `wars.active_wars` — شمارنده‌های تاریخچهٔ شخصیت‌ها هرگز جنگ نیستند).
- `vizier_intrigue` تنها مرجع تفسیر `factions[]` است (خطرناکی فقط با معیار عددی
  `power_over_threshold`).
- `vizier_diplomacy` تنها مرجع تفسیر `succession` است (`algorithm_recomputed` همیشه
  false — سهم‌بندی تقسیم قابل محاسبه از این خروجی نیست) و تنها مرجع تفسیر
  `relations[]` و `dynasty` است (اتحادها/هوک‌های فعال و شکوه/legacyهای دودمان —
  جهت هوک از خروجی قابل اثبات نیست؛ `dynasty.id` ≠ `dynasty.house_id`).
- `opinions[]` (مرحلهٔ ۶) تنها مرجع عدد نظر بین بازیکن و دیگران است — از
  `opinions.active_opinions`، فقط ردیف‌های درگیر بازیکن با `direction` صریح؛
  `total` = مجموع temporary_opinionها؛ بدون temporary مقدار null است (نه صفر) —
  رابطهٔ scripted بدون عدد، نظر عددی ندارد.
- `vizier_intrigue` تنها مرجع تفسیر `schemes[]`، `secrets[]` و `artifacts[]` است
  (دسیسه/راز/شیء؛ شمارش کل در `quality.counts` و نقص‌ها در `quality.missing_counts`).
- `vizier_economy` تنها مرجع تفسیر `domain/counties/holdings` است
  (`domain_count` فقط شهرستان‌های `c_` واقعی — در `quality.counts`).
- نام شخصیت‌ها فقط با مطابقت `id` از `characters[]`؛ بدون تطابق = «map نشده»، نه حدس.

## ۴. جستجوی مسئله و ساخت اسکیل جدید (Dynamic Skill Creation)

اگر در بررسی پروژه یا خروجی JSON به **مسئله، چالش یا مکانیک جدیدی** برخوردی که جزئیاتش را نمی‌دانی:
1. در منابع و ویکی اصلی بازی یا داکیومنت مرجع (`First Version_FINAL_1.pdf`) جستجو کن.
2. راهکار دقیق و راهبردی را استخراج کن.
3. آن را در قالب اسکیل جدید (`.agents/skills/ck3-.../SKILL.md`) ثبت کن — و اگر مسیر
   JSON مرتبط دارد، فیلدهایش را به‌صورت دقیق (`section.field`) در توضیح اسکیل بیاور.
